# Mini-Kafka: Extended Future Roadmap (post Phase 1+2)

**Ordering logic:** data-integrity fixes first (cheapest, most directly extend code you already have) → storage-layer maturity (segments, persistence — these depend on each other) → transport/identity security (independent of storage, but logically layered: encrypt the pipe before authenticating who's on it) → coordination features (biggest, most standalone, correctly last since they're closest to a separate subsystem).

## F.1 — CRC32C Validation on Produce
**Why first:** smallest scope, directly extends the bounds-check parser you already have — same code region, same mental model.
- Parse the CRC field from each `RecordBatch` header.
- Compute CRC32C over the batch payload (Node: `crc-32` or manual implementation for the interview-story value of "I implemented the checksum, not just imported it").
- Reject batches with mismatched CRC — return an appropriate `CORRUPT_MESSAGE` error code instead of silently writing.
**Tests:** produce a valid batch (accepted), produce a batch with one deliberately flipped byte (rejected with correct error code), produce a batch with correct CRC but truncated length (should already be caught by existing bounds check — regression test that both checks coexist correctly).

## F.2 — Rolling Segments
**Why second:** natural extension of the single-segment constant you already isolated (`ACTIVE_SEGMENT`) — this is the next logical maturity step for the storage layer.
- Introduce a size threshold (configurable; small default like 1MB for testability).
- On threshold breach: close current segment, open a new file named after the next base offset, track a list of segments per partition instead of one constant.
- Update index entries to record which segment file each batch belongs to, not just a `bytePos` assumed to be in one file.
- Update Fetch to resolve the correct segment file for a given offset before seeking.
**Tests:** produce enough records to force ≥2 rotations; fetch an offset that falls in the first segment, assert correct data; fetch an offset in the second segment, assert correct data; fetch an offset spanning a rotation boundary (last record of segment 1, first of segment 2) in one request, assert both are returned correctly if the client requested a range crossing that boundary.

## F.3 — Index Persistence Across Restarts
**Why third:** depends on segments existing (the persisted index format needs to reference which segment a batch lives in), so this must come after F.2, not before.
- Periodically flush the in-memory index to a `.index` file per segment.
- On startup/first access, attempt to load `.index` first; fall back to full log scan only if missing or corrupted (checksum the index file itself, or at minimum validate it against the segment's actual file size).
**Tests:** produce records, force an index flush, kill and restart the process, assert first fetch is served from the persisted index without a full rescan (verify via timing or an explicit log line); corrupt the `.index` file deliberately, restart, assert graceful fallback to full rescan rather than a crash.

## F.4 — TLS Transport Encryption
**Why fourth, before SASL:** encrypting the pipe is a prerequisite for authentication to actually mean anything — sending credentials over an unencrypted socket first would be backwards.
- Wrap the raw TCP server using Node's built-in `tls` module instead of `net`, with a self-signed cert for local testing.
- Support both plaintext and TLS listeners on separate ports (real Kafka does this — `PLAINTEXT` vs `SSL` listener configs), so existing CodeCrafters-style tests can still run unencrypted while a new TLS path is added.
**Tests:** connect via TLS client, confirm handshake succeeds and a Produce/Fetch round-trip works identically to plaintext; attempt to connect a plaintext client to the TLS-only port, confirm clean rejection rather than a hang or crash.

## F.5 — SASL Authentication (PLAIN mechanism)
**Why fifth:** now that the transport can be encrypted, credential exchange over it is meaningful rather than security theater.
- Implement the `SaslHandshake` and `SaslAuthenticate` APIs (Kafka protocol keys 17 and 36) supporting the `PLAIN` mechanism (username/password exchange).
- Reject any Produce/Fetch request on a connection that hasn't completed SASL auth, if auth is enabled for that listener.
- Store credentials simply (hardcoded map or a config file) — real Kafka delegates to JAAS, but a minimal credential store is a reasonable, disclosed simplification here.
**Tests:** unauthenticated client attempts Produce, assert rejection with the correct error; client completes SASL handshake with valid credentials, subsequent Produce succeeds; client attempts SASL with invalid credentials, assert clean authentication failure response, not a crash.

## F.6 — Consumer Group Coordination
**Why sixth:** the largest scope item short of replication, and genuinely a separate subsystem (group membership, partition assignment, offset tracking) — correctly sequenced after the storage and security layers are solid, since it builds on top of both (offsets need to be readable via the now-mature Fetch path, and group APIs should also respect auth if F.5 is done).
- Implement `FindCoordinator`, `JoinGroup`, `SyncGroup`, `Heartbeat`, `OffsetCommit`, `OffsetFetch`.
- Maintain an internal `__consumer_offsets`-equivalent structure tracking committed offsets per group/topic/partition.
- Implement basic partition assignment (even a simple round-robin strategy across group members is enough to demonstrate the mechanism).
**Tests:** two consumers join the same group, assert partitions are split between them (not double-assigned); one consumer commits an offset, the other fetches and confirms it sees the committed position; a consumer leaves the group (or times out via missed heartbeat), assert its partitions get reassigned to remaining members.

## F.7 — Basic Replication Simulation
**Why last:** the biggest lift, most clearly a standalone project in its own right, and least likely to be expected in a portfolio-scope implementation — correctly sequenced last, flagged as optional/stretch even within the "future" tier.
- Simplified two-node setup: a leader broker forwards Produce writes to a follower broker over a second TCP connection.
- Follower acknowledges write receipt; leader tracks a basic in-sync-replica (ISR) list.
- Do not attempt full Raft/KRaft consensus — that's a genuinely separate, multi-week distributed-systems project.
**Tests:** produce to leader, assert follower's log file eventually contains the same bytes; kill the follower mid-stream, assert leader continues serving without crashing and correctly reports a shrunk ISR.

---

**Sequencing discipline going forward:** don't skip ahead in this list even if a later item looks more interesting — F.2 depends conceptually on F.1's data-integrity mindset, F.3 literally depends on F.2's segment structure existing, and F.5 depends on F.4 for the security claim to be honest rather than theater. Build in order, or explicitly renumber with a stated reason if priorities change.
